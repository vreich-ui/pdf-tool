### KI-01 — `set_storage_grant` persists to the wrong site (H, confirmed by probe)

- **Evidence:** `netlify/functions/mcp.ts:545,560,730-743` runs the tool inside `runWithRequestContext(ctx)`, which binds the caller's grant in ALS. `mcp-session-grant.ts:48-50` opens the store with `jobBlobStore("mcp-session-grants")` → `artifact-core/blob-store.ts:100-103`, where an ALS grant **wins** over `PDF_TOOL_SITE_ID`/same-site. The later fallback read (`mcp.ts:528`, `readSessionGrant`) runs **before** `runWithRequestContext`, i.e. against pdf-tool's own site. Probe (in-memory store call log, `AGENT_ARTIFACT_MEMORY_BLOBS=1`): the `mcp-session-grants` open during `set_storage_grant` carried `siteID = <tenant siteId>, token = <tenant token>`; the `mcp-sessions` opens carried `PDF_TOOL_SITE_ID`.
- **Failure scenario:** a claude.ai connector calls `set_storage_grant`, gets `ok: true`, then every later call without `storage` fails `STORAGE_GRANT_REQUIRED`. The tenant's Blobs token is also written into a `mcp-session-grants` store on the **tenant's** site, where the tenant may not expect it.
- **Why tests pass:** `tests/agent-artifact-mcp-s4-surface.test.ts` uses the in-memory store, which ignores credentials, so write and read land in the same map.
- **Affected:** `netlify/functions/mcp.ts`, `netlify/lib/mcp-session-grant.ts`, `netlify/lib/artifact-core/blob-store.ts`.
- **Second instance (confirmed 2026-09-06, same probe technique):** the MCP `health` tool runs `probePdfToolOwnStorage()` inside `runWithRequestContext`; with a `storage` grant on the call (or a session grant) the probe's `jobBlobStore("agent-artifact-jobs")` opens the **caller's** `agent-artifact-jobs` store, so the `ok` verdict says nothing about pdf-tool's own storage. Without a grant it probes pdf-tool's own site as intended. The tool description now says to call it without `storage`.
- **Direction:** make own-state openers (`jobBlobStore`) ignore the ambient tenant grant explicitly — or run `setSessionGrant`/`probePdfToolOwnStorage` outside the request ALS — then decide whether to keep persisting tokens at all (KI-10). Add tests asserting the store's `siteID` for both writes (the `health` no-grant case is pinned by `tests/agent-artifact-mcp-metadata-invariants.test.ts`).

### KI-02 — Legacy job endpoints diverge from the shared path (M)

- **Evidence:** `netlify/functions/agent-artifact-job.ts:31-57` calls `validateArtifactJobRequest` + `createArtifactJob` + `triggerWorker` directly — no `policyModelForUsageContext`, no `chargeGenerationBudget`, no cost receipt (`agent-artifact-mcp.ts:107-155`). `agent-artifact-job-status.ts` reads the record without the 12-minute auto-fail, `materializationProof`, `warnings`, `qualityGate` (`agent-artifact-mcp.ts:195-216`). Both are still tested (`tests/agent-artifact.test.ts:9`) and were documented as "existing internal endpoints".
- **Failure scenario:** a caller on the legacy path exceeds the per-request budget without a 429 and never sees a terminal state for a killed job.
- **Direction:** delete both, or make them thin wrappers over the shared handlers. Docs now label them LEGACY (`HTTP_REFERENCE.md`).

### KI-03 — URL import redirect / DNS gap (M)

- **Evidence:** `netlify/lib/image-search/import.ts:45-65` validates only the initial URL, then `fetch` with default `redirect: "follow"`. Contrast `netlify/lib/capture/service-client.ts:170-217` (manual redirects, guard per hop). Neither resolves DNS.
- **Failure scenario:** an agent imports `https://attacker.example/x.png` which 302s to `http://169.254.169.254/...` or `https://10.0.0.5/...`; the fetch follows it. The response must still sniff as an image (or be sharp-decodable) to be stored, which limits exfiltration, but the request is made.
- **Direction:** reuse the `fetchAssetBytes` loop; add a resolved-address check shared by both guards.

### KI-04 — Zip bomb in batch imports (M)

- **Evidence:** `import.ts:134-158`: `unzipSync(new Uint8Array(bytes))` inflates every entry into memory; the per-entry `byteLength > maxImportBytes * 4` check runs afterwards. The download is capped at 4 × 5 MB compressed.
- **Failure scenario:** a 20 MB zip that inflates to gigabytes kills the background function (`image-search-worker-background`), failing the whole batch and possibly co-scheduled work.
- **Direction:** inspect central-directory sizes first, or use streaming inflate with a running budget.

- README said `PDF_TOOL_SITE_ID`/`PDF_TOOL_BLOBS_TOKEN` "are no longer read anywhere" (`artifact-core/blob-store.ts:147-148` reads them; `tests/agent-artifact-blob-credentials.test.ts` pins it); `STORAGE_GRANT_REQUIRED_MESSAGE` (`project-descriptor.ts:307-311`) still repeats the claim to API callers (**code string not changed by the audit**).
- README listed 6 MCP tools at `tools/list`; the server registers 32. Capture docs omitted `get_capture_snapshot`; six template tools and `set_storage_grant`, `inspect_pdf_artifact`, `rasterize_pdf_artifact` were undocumented.
- README said capture output "lands as ArtifactReferences through the storage grant"; it lands in pdf-tool's own site (`capture/storage.ts`).

### KI-06 — Job-record concurrency (M)

- **Evidence:** `agent-artifact-jobs.ts:822-835` (`updateArtifactJob` spreads the record it was handed); worker `:64-79` (no compare-and-set between the read and the `running` write); worker `:68` refuses only `complete`/`running`/`blocked`, so `failed` and `pending` re-run.
- **Failure scenario:** (a) status poll auto-fails a job at minute 12 while the worker is finishing at minute 12.5 → the worker's `complete` write overwrites `failed` (fine) or the auto-fail overwrites `complete` metadata written a moment earlier (data loss depends on timing); (b) an operator re-POSTs the worker for a `failed` image job → a second paid generation and a moved slot pointer.
- **Direction:** version the record (`updatedAt` compare) or use Blobs `onlyIfMatch`/etag where available; make re-runs an explicit tool.

### KI-07 — Partial writes (L)

- **Evidence:** `artifact-layout.ts:125-128` writes bytes, sidecar, then indexes; the job record is updated afterwards (worker `:197`).
- **Failure scenario:** kill between index write and record write → `by-slot` points at the new artifact while the job later reads `failed` `JOB_EXECUTION_TIMEOUT`; a consumer trusting the job status will not find the artifact it could have used, and the bytes are never reclaimed.

### KI-08 — Non-idempotent create (M)

- **Evidence:** `agent-artifact-jobs.ts:805` (`randomUUID` per create); no lookup by `(projectId, requestId, slot|filename)` before creating.
- **Failure scenario:** an agent retries a timed-out `create_agent_artifact_job` call → two image generations billed, two ledger charges (non-atomic, may undercount), the slot pointer ends on whichever finishes last.
- **Direction:** accept a caller idempotency key (or hash of the request) and return the existing job.

### KI-09 — Stranded jobs (L)

- `pending` jobs whose worker never ran and `blocked` jobs never time out; a grant expiry (`storage-grant.ts:164-170`) makes the record unreachable until a fresh grant is minted. No reaper exists. Direction: an expiry on `blocked`, and a documented re-trigger tool.

### KI-10 — Session grants: token at rest, correlation-only sessions (L, design)

- `mcp-session-grant.ts:6-25` states the TTL-only decision. Session ids are random UUIDs but not tied to a client credential (`mcp.ts:483-485`); every holder of `AGENT_RUN_TOKEN`/an OAuth token can use a stored grant by presenting its session id. Acceptable within one trust domain; re-evaluate if pdf-tool ever serves more than one operator.

### KI-11 — Capture plane tenant isolation (M, design)

- `mcp.ts:108-116` makes the capture tools grant-optional; `project-descriptor.ts:465-476` passes with no grant; `capture/storage.ts` writes one site for every project. Any authorized caller can read any project's capture job/snapshot by guessing `projectId` + `jobId` (UUID) — practically limited by the UUID. Decision recorded 2026-08-14 ("option A, same-site writes"); document or add a project check tied to something the caller proves.

### KI-12 — Capture bytes have no export path (M)

- `agent-capture-mcp.ts` exposes only the snapshot JSON (`≤ 8 MiB` inline). Screenshot PNGs and retained asset bytes (`storedArtifact.path`) are written to pdf-tool's own `artifacts` store with no tool, HTTP route or signed URL to fetch them. The consumer (CMS-Agent `emit.mjs`) therefore cannot use `storedArtifact` without pdf-tool's Blobs credentials. Direction: a `get_capture_artifact` tool that streams by `path`+`sha256`, or a copy-to-tenant-store step under the caller's grant.

### KI-28 — Agents-SDK wrapper around image generation (M, medium confidence on consequences)

- **Evidence:** `agent-artifact-workflow.ts:73-87,172-177`: every image job constructs an `@openai/agents` `Agent` with one tool and calls `Runner.run` (SDK default model `gpt-4.1`, `node_modules/@openai/agents-openai/dist/defaults.js`), instructed to call the tool once; if no bytes were produced the tool is called directly. All tests set `AGENT_ARTIFACT_TEST_AGENT_SDK=1`, which replaces the SDK with `{}` so the loop never runs under test.
- **Consequences (facts → likely):** one extra LLM round-trip per image job (cost/latency); `OPENAI_API_KEY` is required even for fal.ai jobs; if the SDK reports a tool exception to the model instead of throwing, the model may call the provider again (double spend on transient failures) and the real error is replaced by a generic "did not produce bytes"; the production path has zero test coverage.
- **Direction:** call the provider directly (the tool handler already contains the whole workflow) or make the SDK loop opt-in and tested.

### KI-29 — A status poll is a write (L, architectural smell)

### KI-30 — `image.annotate` text-fitting error: FIXED for the six bundled Noto faces, still heuristic for anything else (M -> partially closed)

- **What changed (font-metrics branch):** `resolve.ts`'s `defaultMeasureText` now measures EXACTLY for the six bundled Noto faces (NotoSans/NotoSerif, regular+bold) instead of guessing. `netlify/lib/image-annotate/font-metrics-data.ts` is a per-codepoint glyph-advance table generated by `scripts/generate-font-metrics.mts`, which parses each `render-service/fonts/*.ttf`'s own `head`/`hhea`/`hmtx`/`cmap` tables directly (hand-rolled, no new dependency; cross-validated codepoint-for-codepoint against `fontTools` while building this fix). `resolve.ts`'s `resolveBundledFace` decides, from the resolved `font-family` string alone, whether resolve.ts can be SURE the render service will actually use a bundled face (a narrow, explicit set: CSS generic keywords `sans-serif`/`serif`/`system-ui`/etc. and the bundled faces' own literal names — deliberately narrower than render-service's own larger named-brand alias table, and NOT including `NotoSansHebrew`, which — see below — is not actually reachable through this feature's font resolution today). `ADVANCE_RATIO` remains the fallback for anything else: a per-request uploaded font (resolve.ts is never given the request's `fonts[]` list), an unrecognized family, or a codepoint the resolved face's cmap doesn't cover. `TextPlacement`/`BadgePlacement` now carry `measurementSource: "metrics" | "heuristic" | undefined`, and a `MEASURED_BOX_DRIFT` warning's `detail.measurementSource` says which path produced the drifted prediction — the "make it observable" half of the fix (see `docs/IMAGE_PIPELINE.md` §2.5).
- **Verified against real Chromium, not just unit assertions:** `render-service/tests/agent-artifact-image-annotate-nac-regression.test.ts` reproduces the EXACT production incident (a 30.72px ALL-CAPS "NAC" label, 1024px canvas) — the old heuristic's 47.92px predicted width wraps to two lines on real Chromium (h~=76.8px), the new exact width (62.39px, NotoSans-Regular's real N+A+C advances) renders on one line and matches Chromium's own measurement to within its documented `MEASURED_BOX_DRIFT` tolerance. `render-service/tests/agent-artifact-image-annotate-hardcases-investigation.test.ts` extends this to an all-narrow string (heuristic 2x too wide), an all-wide string (heuristic ~43% too narrow) and a mixed sentence (see the kerning finding below) — all measured against real Chromium, numbers printed to the test log. The existing adversarial golden fixture's own ALL-CAPS element ("MAXIMUM WATTAGE WARNING") now predicts the SAME two-line wrap real Chromium renders (previously it predicted one line and silently drifted) — `tests/fixtures/image-annotate/png-golden.json`'s `elementMeasurements` for `.ann-shout` went from a mismatch against an `h:18` prediction (pre-fix) to matching the regenerated `h:36` prediction exactly.
- **Two findings this fix surfaced, neither hidden:**
  1. **Kerning is not always zero.** For a monotone string (all-caps, all-one-glyph-class) sum-of-advances matches real Chromium to a fraction of a pixel. For ordinary running prose, Chromium's default `font-kerning: auto` measurably contracts the text relative to a pure advance sum — measured at ~0.5% (1.4px on a 303px, 24px-font sentence), confirmed by re-measuring with `font-kerning: none` (which lands back within 0.01px of the sum-of-advances prediction). This is comfortably inside `MEASURED_BOX_DRIFT`'s tolerance (max of 10%/2px) so it does not by itself misfire a warning, but "exact" here means "exact for the adversarial cases that actually break the old heuristic," not "byte-identical to Chromium's shaper for every string." See `resolve.ts`'s `defaultMeasureText` scope note.
  2. **NotoSansHebrew is bundled but currently unreachable.** `render-service/src/fonts.ts`'s `bundledFallbackFamily` only ever resolves a template's `font-family` to `"NotoSans"` or `"NotoSerif"` — there is no code path today by which an AnnotationSpec's `theme.fontFamily` causes NotoSansHebrew to be selected for rendering (a pre-existing gap, not introduced by this fix, and out of scope for it — it lives in render-service's font classification, not in resolve.ts's measurement). Because of that, `resolveBundledFace` never returns a Hebrew face; testing whether sum-of-advances is even a reasonable model for Hebrew required forcing NotoSansHebrew via a per-request UPLOADED font (bypassing the classifier). On that controlled test (a plain two-word RTL string, no niqqud, no mixed scripts), sum-of-advances predicted within 0.2% of Chromium's real measurement — Hebrew's square script has no contextual joining, so bidi reordering moves glyph POSITIONS, not the total advance sum. That is one data point, not a proof for every Hebrew case, and the more consequential gap (nothing selects NotoSansHebrew in production) remains open — worth its own KI if Hebrew annotation is ever a real requirement.
- **Freshness:** `tests/agent-artifact-font-metrics-freshness.test.ts` re-hashes the live `render-service/fonts/*.ttf` files against each face's embedded `sourceSha256` — a font swap that lands without re-running `scripts/generate-font-metrics.mts` fails this test loudly, the same discipline `tests/agent-artifact-image-annotate-goldens.test.ts`'s `fonts.json` golden already applies to the raw font bytes.
- **What remains open (unchanged from before this fix):** anything that reaches the heuristic — a per-request uploaded font (resolve.ts has no visibility into `AnnotationRenderInput.fonts`, so it cannot tell "this family will be honored by an upload" from "this family is genuinely unknown"), a named brand alias resolve.ts doesn't recognize (`Arial`, `Georgia`, ... — render-service would still fall back to a bundled face for these, but resolve.ts deliberately does not assume that without duplicating render-service's larger alias table), and any non-Latin/non-Hebrew script — still gets `ADVANCE_RATIO`'s "+/-15% typical, correct-or-one-extra-line worst case" estimate, diagnosed post-render exactly as before. This module still does not re-resolve or re-render on drift — the reported drift remains a diagnosis, not a correction.

### KI-32 — No face/subject-aware avoidance; `avoid[]` accepts geometry only (L)

- **Evidence:** `spec.ts`'s `avoid` field is `z.array(rectSchema)`, and `rectSchema` is strictly `{at: Cell|Point, w, h}` — there is no string/enum branch anywhere in the AnnotationSpec schema that could accept a semantic tag. `analyze.ts`'s `LayoutHints.faces` is typed `never[]` and is unconditionally `[]`; `subject` is unconditionally `null` (module doc: "Face/subject detection is Phase 2 ... `faces` and `subject` are stable placeholders for now"). - **Correction to an earlier description of this limitation:** a form of this gap was described (before this doc pass) as "`avoid: ["faces"]` is a no-op" — that is not what the code does. Passing a string where `avoid[]` expects `{at, w, h}` objects fails zod validation and the whole `annotate_image` call is refused with `TEMPLATE_INVALID`, loudly, not silently accepted and ignored.
- **Failure scenario:** a caller who expects semantic avoidance (as some prior planning language implied) gets a hard schema-validation refusal, not a soft no-op. Nothing in this feature can currently answer "where is a face in this image" — the only substitute is `analyze_image_layout`'s `safeZones` (busy/luminance-scored, not subject-aware) or manually eyeballing `preview_image_grid`'s output and hand-picking a rect.

### KI-33 — Contrast check samples the base photo only, not what actually paints behind text (L)

- **Evidence:** `render.ts`'s `buildLuminanceSampler` doc comment states two "honest limitations, both documented rather than hidden": it "samples the BASE IMAGE ONLY. A text element that sits on top of a spec-authored scrim or a filled box is measured against the photo underneath, not against the surface it will actually be painted on, so its reported ratio is pessimistic," and it is a coarse 32×32 average (`LUMINANCE_GRID_EDGE`), so "a caption over a hard black/white boundary reads as mid-grey."
- **Failure scenario:** a spec paints a strong dark `scrim` (`strength: 0.8`) behind a white title. The photo underneath happens to be light at that spot, so the sampler (checking the raw photo, not the scrim-darkened composite) reports `CONTRAST_LOW` and inserts a redundant second auto-scrim on top of the caller's own — unnecessarily darkening the image. The mirror case is worse: a caller-authored `box` with a light, opaque fill behind text gets no contrast credit either — `CONTRAST_LOW` can still fire even though the rendered pixel the text actually sits on is fine, OR (if the photo underneath happens to be dark) the check can pass while the ACTUAL fill the text sits on is genuinely low-contrast, since the sampler never looks at the fill color at all.
- **Direction (not implemented):** sample against a simulated composite — the base image plus every already-resolved `scrim`/`box` placement painted at its own pixel position and opacity — rather than the raw base image, before deciding whether an auto-scrim is needed.

### KI-39 — an exact-fit text box had zero slack, and a bottom-anchored box that grows could run off the canvas (M, fixed in this branch)

- **Defect 1 — CSS width with zero slack wraps on a sub-percent gap.** `render.ts`'s `textRules` set a text block's CSS `width` to EXACTLY the resolver's predicted `box.w` (see KI-30). Even the bundled-face exact metrics table is a sum of per-glyph advances with no kerning/shaping/device-pixel snapping, and real Chromium's own text layout can legitimately need a hair more than that sum — confirmed by sweeping real Chromium (not assumed): "TTJVOMQH" set bold at the `title` style's font size on a 1024px canvas edge (51.2px) predicts 277.76px from NotoSans-Bold's own glyph advances, but Chromium's natural (unconstrained) width for the same run is 278.22px — a 0.46px/0.16% gap — and a box sized to exactly 277.76px wraps to two lines. **Ceiling to the next whole CSS px is not enough on its own**: 278px is still short of the 278.22px Chromium needed; a longer ALL-CAPS run at a larger font size needed ~5px (~0.35%) more than predicted in the same sweep, i.e. the residual scales with the predicted width rather than being a fixed sub-pixel amount.
  - **Fix:** `render.ts`'s `widenedTextBox` adds `max(TEXT_WIDTH_SLACK_MIN_PX=1, box.w * TEXT_WIDTH_SLACK_FRACTION=0.01)` of slack to the CSS width — a full order of magnitude below `MEASURED_BOX_DRIFT_FRACTION` (10%) so this slack can never itself mask a real `MEASURED_BOX_DRIFT`, with ~3x headroom over the largest residual the sweep found. The slack is applied **align-aware**: `left` unchanged for `align:"left"` (extra width goes right), `left -= slack` for `align:"right"` (right edge unmoved), `left -= slack/2` for `align:"center"` (center unmoved) — so resolve.ts's own `box` (used for anchor placement, collision push-out and canvas clamping) is never touched, and neither is the edge alignment actually renders text against. Verified against real Chromium (not just the arithmetic): `render-service/tests/agent-artifact-image-annotate-ki39-width-slack-regression.test.ts` measures the box's real center/right edge after widening for `align:"center"`/`"right"` and confirms neither moved.
  - **What moved in the goldens (and what didn't):** every affected fixture (`tests/fixtures/image-annotate/document/*.txt`, `resolve/multi__*.json`'s box widths) shows the widened `width` (and, for the one existing `align:"center"` unit-test fixture, a compensating `left` shift) — `x`/`y`/`h` are untouched everywhere. The real-Chromium PNG golden (`png-golden.json`) shows every `elementMeasurements` entry's `w`/`scrollW`/`clientW` grow by the slack and **`x`, `y`, `h` unchanged on every element** — and `pngSha256` itself did not change at all, since none of that fixture's text elements are `align:"center"`/`"right"` (their CSS `width` has no visible background/border, so widening it moved no rendered pixel).
- **Defect 2 — a bottom-anchored box that grows could run off the canvas.** `resolve.ts`'s `clampToCanvas` only ever sees the PREDICTED box; a text block's CSS never sets `height` (so it can grow downward at real-render time — see render.ts's module doc), so a caption anchored at the bottom edge whose predicted single line is, on real Chromium, actually two (a genuine measurement miss — confirmed via the documented "named brand font" heuristic-path gap: `font-family:"Arial"` measures with `ADVANCE_RATIO` here while render-service's own font resolution still renders it as NotoSans) grows straight past the canvas edge: `top` never moves, only `height` grows, and anything below the viewport is not in the rendered image at all. Confirmed against real Chromium: a `title`-style "MMMWWW" caption anchored `bl` flush against a 1024px canvas needs 128px (two lines) where 64px (one line) was predicted, and with the pre-fix box.y (960) the real box's bottom lands at 1088px — 64px (one full line) outside the 1024px canvas.
  - **Fix:** `resolve.ts`'s `reserveTextGrowthHeadroom` runs once per text placement, after `clampToCanvas`, and shifts the box UP (never past y=0) by `TEXT_GROWTH_RESERVE_LINES(1) * fontSizePx * DEFAULT_LINE_HEIGHT_MULTIPLIER` whenever the predicted box plus that reserved line would not otherwise fit — a deliberate, documented bound (one extra line, matching KI-30's own observed error bar: "correct, or one whole extra line", never "many"), not a guarantee against an arbitrarily large misprediction. When even shifting to y=0 cannot make up the reservation, it warns `TEXT_GROWTH_HEADROOM_INSUFFICIENT` (new `WarningCode`, carrying `shortfallPx`) rather than silently leaving the box to crop. Only `text` placements are affected — badges/boxes/scrims/logos have a fixed, predicted-exact CSS box with no growth path. On the "MMMWWW" case above, the reservation shifts box.y from 960 to 896; the real 2-line box's bottom then lands at exactly 1024px (flush with the canvas edge, confirmed against real Chromium, not just the arithmetic).
  - **A real, documented trade-off:** the reservation runs AFTER push-out/collision, so a box shifted up for headroom is not re-checked against `avoid[]` zones or other elements — it could end up overlapping something above it. Left as-is: the alternative (the box exactly where the predicted-height clamp put it) is the defect this closes, and BRIEF.md's failure model (warn, never silently crop or misrender) rules out silent cropping as the worse trade.
- **Verified against real Chromium, not just unit assertions:** `render-service/tests/agent-artifact-image-annotate-ki39-width-slack-regression.test.ts` (defect 1: OLD zero-slack width wraps, ceil-to-integer still wraps, NEW slack-widened width renders one line for `align:"left"`/`"center"`/`"right"` with the anchored edge unmoved) and `render-service/tests/agent-artifact-image-annotate-ki39-bottom-growth-regression.test.ts` (defect 2: WITHOUT the fix the real second line overflows the canvas by ~one line, WITH the fix it lands flush inside) both reproduce the exact numbers above through `/render/image` — the same route `annotate_image` calls. `tests/agent-artifact-image-annotate-growth-headroom.test.ts` is a companion Chromium-free suite pinning `reserveTextGrowthHeadroom`'s arithmetic directly (including the `TEXT_GROWTH_HEADROOM_INSUFFICIENT` shortfall path and the "only text is shifted" invariant).
- **What remains open:** `TEXT_GROWTH_RESERVE_LINES=1` is sized to the observed failure mode, not to an arbitrary number of mispredicted lines — a spec whose heuristic-measured text is wrong by more than one line's worth still risks the same defect, now reported via `TEXT_GROWTH_HEADROOM_INSUFFICIENT` instead of silently cropping, not corrected. Defect 1's slack is likewise a documented bound (1%/1px) grounded in the largest residual gap this fix's own Chromium sweep found (~0.35%), not a formal proof that no larger residual exists for some other font/glyph combination.
